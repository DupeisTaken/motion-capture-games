# Mirror application

## Entry points

The root URL and `/index.html` serve the game directory. It links to all four implemented games: `/mole.html` (Slap a Mole), `/dodgeball.html`, `/runner.html` and `/maze.html` (Virtual Maze), plus `/diagnostics.html` (tracking console) and `/rig.html` (two-camera workspace). Game headers expose **All games**; the Motion Studio brand returns to the directory. Console links explicitly target `/diagnostics.html`, replacing the old root route.

Directory content is static HTML, with local CSS and a CSS-only module entry for the Vite artifact check. Links remain usable with JavaScript disabled. Loading it imports no game, camera, inference or diagnostics runtime and makes no vision-service requests. Each game keeps its own input setup and scoring. Virtual Maze is clearly labeled synthetic rehearsal with physical input pending.

Run `pnpm exec vite` for frontend-only browsing after installing dependencies, or `pnpm dev` for the complete application. Run `pnpm verify:directory` for real-server desktop/mobile navigation evidence and `pnpm verify:directory --production` after `pnpm build` to verify emitted routes. See [the delivery report](../../reports/game-directory.html).

When adding a playable HTML entry, register it in `vite.config.ts`, add a directory card with accurate input requirements, update this entry-point list and the [CI component/build table](../../docs/continuous-integration.md#component-and-package-builds). The directory test compares game links with actual app HTML entries to catch omissions.

## Runtime composition

`rig.html` provides the [two-camera operator rehearsal and physical planning workspace](../../docs/two-camera-workspace.md). Both camera diagnostics remain prominent, with XYZ separate from the player display. **Gameplay camera** selects the synthetic background for one real Slap a Mole Practice/Touch runtime and its optional player window. A fresh synthetic pointer/keyboard controller drives hits; recorded bodies/XYZ do not. The inline gameplay preview starts collapsed, and only its game stage/HUD moves to the player window. Identity, source-quality, clock and lifecycle boundaries are documented in the owning guide. No capture, inference or simultaneous live cameras are added. [The gameplay-camera report](../../reports/displayed-camera.html) records actual verification.

Virtual Maze uses the same `pre-game-settings` dialog/controller as the other games. `maze-setup.ts` owns draft configuration and native validation; Start round commits a prepared maze, while Close/Escape preserves the paused current round. `maze-camera-guide.ts` provides an accessible placement schematic and practical calibration/accuracy steps without opening cameras or certifying a rig. The shared controller's optional `canStart` guard validates before closing; its default behavior for existing games is unchanged.

`maze.html` adds the camera-free [Virtual Maze](../../docs/games/virtual-maze.md) rehearsal. `maze-viewer.ts` composes the pure maze engine, explicit head/torso input validation, an operator-only metric map, local photo corner annotations and a map-free participant view/window. `maze-audio.ts` owns explicitly enabled browser sound and immediate silence on pause/input loss. No camera API is called. Live two-camera XYZ and physical orientation remain gated. `pnpm verify:maze` records real-server English desktop/mobile evidence; [the report](../../reports/virtual-maze.html) records actual results.

Both game viewers default to Camera, enumerate device metadata on load and acquire capture only after **Start camera**. Rehearsal remains selectable. Facing the display, leftward movement appears leftward in the mirror; pointer and arrow controls invert display coordinates back into canonical input exactly once. Mole targets use the shared `mapJoint` presentation helper, matching contacts and video in both inline and separate game windows. [The delivery report](../../reports/camera-default.html) records tests and synthetic browser evidence.

The TypeScript diagnostic viewer renders an independent camera image and source-timed canonical skeletons with Canvas2D. It automatically shows current detected-person count, camera-local association states, source controls and diagnostic timing. It does not acquire diagnostic frames or import inference libraries. Explicit browser discovery and temporary identification can open a setup-only stream; its tracks are released before Python capture starts. Browser IDs are never guessed to be native indices.

Run `pnpm dev` at the repository root. [The viewer guide](../../docs/diagnostic-viewer.md) describes setup and controls. The display-clock frame loop keeps one decoded image, while independent image and pose streams each request their next current item after consumption; display mirroring applies equally to video and geometry. Stop/restart, missing input and source epochs invalidate old observations and image bitmaps.

`mole.html` now composes the experimental [Slap a Mole game](../../docs/games/mole-motion.md), game-ready motion contacts and one explicit session slot. `mole-viewer.ts` owns controls, bounded camera packet delivery and labeled synthetic rehearsal; `mole-renderer.ts` shares contain/mirror geometry between video, targets and contacts. The production renderer/media path remains future work. [ADR 0005](../../docs/decisions/0005-diagnostic-skeleton-slice.md) limits the camera transport; [ADR 0002](../../docs/decisions/0002-provisional-runtime-and-media.md) still owns the larger performance experiment. Tests include simulated DOM integration and separately reported real-server screenshots.

`camera-release.ts` retains acknowledged source epochs until their scoped stop is acknowledged. Failed HTTP/network cleanup remains visible and retryable across source selection; an ended preview does not prove driver release. Game Start records intent before readiness and admits a unique stable participant; missing joints can recover through countdown while explicit identity loss requires a new round. `game-display.ts` moves the same stage/HUD/listeners to a separate browser window, migrates its ticker, restores focus/order on return, and never opens a camera or creates a second session. Game tracking graphics default off and stay hidden in the separate display; camera pictures have no tint/mask.

The diagnostic console also uses `CameraReleases`. Startup, local display and acknowledged release have separate state; one teardown invalidates both streams, animation and pending bitmap work. Stop/hidden/pagehide during startup waits for the owned acknowledgment instead of sending an unscoped stop. Failed cleanup keeps retry visible and replacement locked. A lost startup response cannot be associated safely through shared status; see [ownership and recovery](../../docs/diagnostic-viewer.md#capture-ownership-and-retry).

Game composition supports camera-overlay games and the [motion runner's rendered world](../../docs/games/motion-runner.md#presentation-and-player-admission). `runner.html` composes original Three.js worlds, camera-free rehearsal, canonical camera pose calibration/practice, one-player admission and fair recovery. It never renders camera images, including setup and practice. [The implementation report](../../reports/motion-runner-game.html) records software evidence; physical control tuning remains open.
unner.html now composes the experimental runner: a Three.js rendered world, camera-free rehearsal, canonical camera pose calibration/practice, one-player admission and fair pause/recovery. It never renders camera pixels. See the [runner design](../../docs/games/motion-runner.md) and [implementation report](../../reports/motion-runner-game.html); physical control tuning remains open.

Render, camera/source and pose FPS are measured separately. Telemetry/person-list DOM work is limited to 4 Hz; overlays outside the 150 ms source-time hold window are hidden. [ADR 0006](../../docs/decisions/0006-independent-preview.md) records the tradeoff.

Operator telemetry updates at most four times per second, using a bounded 120-pose window. Person rows change only when displayed identity/joint-count/capacity information changes; the canvas draws on its independent display clock. Controls, stage timings and stream context share one responsive page. See [the console report](../../reports/diagnostic-console.html) for actual measurements and verification.

`dodgeball.html` composes the experimental [Dodgeball game](../../docs/games/dodgeball.md). It adds full-body rehearsal/camera input, shared contain/mirror placement for visible collision shapes and ball warning rings, explicit joining and framing recovery. Run the same local server; rehearsal needs no camera service. The game owns collisions and score while this app owns transport and controls.

`pre-game-settings.ts` owns the shared native setup dialog and confirmation/focus lifecycle for both games. Video/input and game options share one menu, opened on load and before every new round. The viewer resets ownership/score only on Start confirmation, retains selections, locks setup during ordinary active play, and keeps Pause/Resume plus camera stop/release retry on the operator page. The same camera release controller serves the menu and game page; no additional capture, inference or session runtime is created. [The setup report](../../reports/pre-game-settings.html) records actual behavior tests and browser evidence.

The production frontend includes [third-party runtime notices](public/THIRD-PARTY-NOTICES.txt) for bundled dependencies. The procedural runner worlds and character models are original assets.
