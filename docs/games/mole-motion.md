# Slap a Mole

Slap a Mole is the experimental single-player whack-a-mole slice tracked by [issue #12](https://github.com/DupeisTaken/motion-capture-games/issues/12). It starts M2 software development at the user's request; M1 camera, identity, latency and hardware certification remain open. It must not claim production readiness or multiplayer certification.

The public name is **Slap a Mole**. The existing `/mole.html` route and `games/mole-motion` source path stay stable for existing links and imports. [Issue #42](https://github.com/DupeisTaken/motion-capture-games/issues/42) and the [rename verification report](../../reports/slap-a-mole-rename.html) record the branding change.

## Rules and controls

**Camera** is the default input. Device discovery runs on load; capture still requires **Start camera**. **Rehearsal** remains an explicit camera-free option. Facing the display, stepping left moves the mirrored image left, and stepping right moves it right. Pointer/touch positioning and arrow keys follow those same screen directions, including in the separate game window. Canonical coordinates and anatomical joint names remain unmirrored; targets and contacts use the same presentation transform as the image.

The **Video & game settings** menu opens when the page loads and before every new round, including **Play again** and identity-recovery restarts. Video/input, named camera selection, rehearsal controls, display options, mode, difficulty and Touch/Flick/Push live together there. **Set up round** opens the menu; only its **Start round** confirmation clears previous results and requests play. Closing setup or pressing Escape without editing settings preserves the current results and does not start a round. Choices remain selected between rounds. Active rounds lock configuration; Pause/Resume stay on the game page and do not reopen setup. Camera acquisition still needs **Start camera**. Stop and acknowledged-release retry remain available both in setup and on the game page. On narrow screens the options scroll between a fixed menu header and Start action. [Issue #33](https://github.com/DupeisTaken/motion-capture-games/issues/33) and [the setup report](../../reports/pre-game-settings.html) track this flow.

Random moles appear in a bounded normalized camera-image play area. Touch mode hits a mole with an observed hand/wrist or foot/ankle proxy. Push mode requires an eligible hand, wrist or hip to move toward the screen while overlapping a mole. Push is a depth capability: existing 2D camera adapters cannot supply it. A labeled synthetic rehearsal supplies depth; the camera UI must explain and gate push rather than invent depth from image size. Each target scores once. A held touch must exit before rearming against a newly spawned target. Push needs a fresh return-and-push cycle; switching contact names cannot bypass this rule.

**Flick** adds a 2D wrist-flap alternative ([issue #29](https://github.com/DupeisTaken/motion-capture-games/issues/29)). Select Flick, hold either wrist near the mole, then make a short quick flap. Briefly settle your hand before the next whack. Rehearsal uses a quick cursor movement or arrow-key tap after aiming and settling. Feet and hips cannot flick. Touch and depth-only Push retain their existing rules. Current body-pose providers track wrist position, so a flap must visibly move the wrist; finger-only movement or rotation around a stationary wrist cannot be detected.

Flick uses mapped **source** intervals, with at least 0.018 normalized image travel at 0.35 image units/second within 120ms. Paths over 0.12 image units are rejected as jumps. Its swept path must pass within the target radius plus 0.035 image units, allowing a hand-sized margin and movement between samples. These image units are not calibrated meters. A 180ms settle within radius 0.008 arms each limb; a flick consumes that cycle even on a miss or during countdown/target expiration. History is bounded to 16 samples per limb, and clears on missing limbs, hand/wrist alias changes, sample gaps over 120ms, pauses and all existing invalid-input boundaries. No queued gesture can score after recovery. These defaults live in `TUNING.flick` and need physical sensitivity/playtesting; they do not establish hand-orientation recognition or measured latency. [The flick report](../../reports/wrist-flick.html) records software and browser evidence.

Timed lasts 60 active seconds; Challenge aims for 15 hits in 60 active seconds; Survival ends on the third expired mole; Practice is untimed without miss penalties. Pause, framing/tracking loss and readiness freeze round and target time. A transient joint/framing interruption recovers automatically after fresh input is steady for 600ms, followed by a two-second countdown. Operator pauses and hidden displays require Resume. Recovery clears gesture history and never catches up missed time. The 600ms hold is proposed software tuning, not measured physical identity certification.

Camera play requests the paired image and pose stream only, so the vision service can skip the additional JPEG stream used by the tracking console.

Easy/normal/hard vary target size and lifetime. Hard samples 32 candidates and favors the greatest minimum distance from currently available eligible contacts; missing contacts are excluded. The full target radius stays inside the configured play area; that image-space boundary is not yet a measured participant reach calibration. Difficulty never enlarges it. Defaults are unmeasured tuning proposals owned by `TUNING` in the game module.

| Setting                                | Easy  | Normal | Hard  |
| -------------------------------------- | ----- | ------ | ----- |
| Normalized image-space radius          | 0.065 | 0.052  | 0.040 |
| Target lifetime in active milliseconds | 3600  | 2500   | 1700  |

The default play rectangle is x=0.12, y=0.16, width=0.76, height=0.68. Push arms at displacement <=0.04m and hits on a fresh crossing >=0.12m while overlapping; any forward attempt consumes the cycle, even on a miss. These thresholds need calibrated depth and physical trials. Scoring awards 100 per hit plus 10 per consecutive hit above the first, capped at a 100 bonus. Escape resets the streak; Practice records no miss penalty. Start countdown is 3 seconds; resume is 2. The input freshness limit is 350ms; update interruptions over 400ms pause. User-facing new rounds receive a fresh random seed; the engine accepts an explicit seed for reproducible tests and replay.

## Ownership and input boundary

`packages/motion/src/game-input.ts` exports model-independent `MotionContact` and `GameMotionFrame`. Contacts use anatomical names and upright unmirrored normalized image x/y; optional `towardScreenM` is positive toward the screen relative to a stable calibrated reference. `atMs` is mapped source time on the browser monotonic timeline, not wall time. A frame carries version 1, epoch, sequence, slotId, identity, feetVisible, depthAvailable and spaceRevision. No provider indices enter games. Presentation mirrors both targets and input exactly once and contain-fits them with the video.

`packages/session` owns binding one confident camera-local track to the anonymous player-1 slot. The app automatically requests that binding only when exactly one unique confident track is available, or when the operator chooses an explicit advanced override. It never selects by array order or x position. Start expresses round intent immediately, including while tracking is incomplete; no score or round time advances until required input is steady. The round pins the exact track, source epoch and camera space. Its game-frame revision includes that track; another track never inherits its score. Camera track association remains experimental and is not M1 identity certification.

`games/mole-motion` owns seeded target selection, collision, score, active game timeline and replay. The app owns camera control, bounded source-aligned packet delivery, video, controls and synthetic rehearsal. No camera or inference imports belong in a game. The existing diagnostic page remains available. Source time mapping preserves bigint nanosecond differences and processing age; the initial transport offset remains unknown. Targets are evaluated on the current active browser timeline with no exposure-based latency compensation. This is conservative software behavior, not verified exposure synchronization or physical motion-to-display latency.

Hit regions are circular in normalized image coordinates, so their displayed boundary is elliptical on rectangular images. Video, contact indicators and that boundary use the same contain-fit rectangle and one mirror transform; anatomical labels remain stable. The camera image is mirrored and contain-fitted without a full-frame tint or mask. Skeletons, track labels, contact markers and the play-area guide are hidden by default; the operator can enable tracking diagnostics. Rehearsal retains its aiming cursor. A separate game window moves the existing stage, targets and live score/time HUD to another display without opening another camera or game runtime. Diagnostics stay out of that player display; closing it returns the stage to the operator page. The app never imports a model or opens a camera; `/api/start` delegates acquisition to the existing vision process.

## Framing and failure policy

Both feet must be confidently observed in frame. Otherwise show “Step back — keep both feet in view” and suspend scoring/timers. Foot loss alone does not establish camera distance: explain that the participant may also need camera adjustment or to clear an occlusion. Missing eligible contacts, stale/future/non-monotonic samples, ambiguous identity and unavailable push depth cannot score. Clear motion history across all such discontinuities. Spectators never inherit the slot or score. A tab becoming hidden pauses play.

The game exposes a read-only `readiness(nowMs, frame)` query. Start stays available without a valid pose and arms a waiting round; End cancels that intent. A sole confident track is bound automatically. Multiple candidates produce a clear waiting message; advanced participant selection is optional and remains usable before the round starts. Pose movement or detection order does not recreate selector options.

Missing joints/feet freeze score and time, keep ownership pinned, and recover automatically when the same confidently identified track is ready. A transport interruption up to two seconds can similarly recover if no intervening packet explicitly lost identity. An explicit ambiguous/unassigned identity, an absent/replaced pinned participant, a longer interruption, or a source/clock/calibration/geometry change requires **Start new round**. That action opens setup; its Start round confirmation clears the previous score and arms a fresh round. No separate Join step is required. A returning ID after explicit identity loss cannot resume the previous score. These are conservative software rules, not proof of physical reidentification.

The camera remains visible under compact local pause/countdown notices. Only an entirely hidden game pauses for visibility; a visible separate game window continues if the operator tab is hidden. Operator Pause and hiding every display require Resume. Holding Space suppresses browser scrolling while only the first keydown creates a rehearsal push.

Camera release is acknowledged separately from ending the local preview. The app retains each acknowledged source epoch through HTTP 409 or network failures, displays “Camera release unconfirmed,” and offers an epoch-scoped Retry camera stop, including after switching to rehearsal. New camera setup is blocked until cleanup is acknowledged. Closing a socket is not proof the camera driver released capture. No retry sends an unscoped stop command.

## Verification and gates

Seeded game-input replay version 1 reproduces targets, scores and outcomes for the same commands and timestamps, including new `interaction: "flick"` replays. Existing touch/push replay behavior is unchanged; older engines do not accept the added interaction value. Tests cover every mode, all three hit modes, source-timed flick speed/travel and swept collision, jitter/drift/jump rejection, one-shot/rearm rules, hard-placement bias, bounds, stale and malformed input, framing loss, identity/epoch/calibration changes, source ordering, pause/recovery, end/restart and UI configuration. Real-server English desktop/mobile screenshots verify the delivered interface using synthetic data. Physical flick sensitivity/pushes, actual camera framing accuracy, participant reach calibration, Windows/macOS hardware capacity, three-player attribution and physical latency still need measured trials.
