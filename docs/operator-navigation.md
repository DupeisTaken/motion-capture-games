# Game and operator navigation

Every top-level page has the same **All games** return link, current location and **Switch view** button. Open Switch view for all four games, the tracking console and two-camera workspace. The directory remains available at `/` (and `/index.html`); its static cards and tool links also work without JavaScript.

The GitHub Pages build offers the directory and four rehearsal games only. Its chooser omits operator tools that are not shipped. Relative destinations preserve the repository's project path, including current-location detection and departure guards; the local build retains all seven destinations.

The location distinguishes **Game & controls**, **Operator tool** and **Game directory**. Operator navigation stays in the owner document, outside game stages. Separate participant windows contain only their existing game presentation and return controls. Moving the stage never moves navigation or starts another camera.

The tracking console contains single-camera setup. Two-camera workspace opens role planning and synthetic XYZ rehearsal. The local Maze setup contains sequential live floor calibration, with its own capture owner. These tools do not enable physical maze gameplay or synchronized live XYZ.

## Keyboard and mobile

Tab to **Switch view**, then Enter or Space to expand it. Tab follows ordinary links through Games and Operator tools. Escape closes the list and returns focus to Switch view. The button reports its expanded state, the destination marks `aria-current="page"`, and links/buttons have visible focus and at least 44-pixel target height. Mobile wraps the same destinations into a single column; none are removed. English is the only supported language.

## Switching safely

Changing pages ends the current round and resets unsaved in-memory settings. It does not transfer a score, source or camera to the destination. Capture still needs an explicit Start camera action there.

An operator with active capture must use the existing **Stop camera** (or tracking-console **Stop**) before switching. An unconfirmed release keeps the current page and its **Retry camera stop** controls available. A cancelled Start remains pending through its late acknowledgement and any scoped release. Mole, Dodgeball and Runner apply the same pending/unknown barrier to acquisition: Start camera, camera selection and input-source selection remain locked after local Stop until acknowledged cleanup completes. Unknown startup ownership requires restarting the local vision service, then reloading the page; this affects all tabs sharing the service. Navigation never sends an unscoped stop or guesses ownership from global service status.

The browser identification preview in the console must also be released. Return or close a separate participant window before switching. A focused status message explains a blocked departure; it does not dismiss the source's existing retry UI. Current-location links do not reload the page. Modified clicks and links explicitly targeting a new tab retain ordinary browser behavior because they leave this owner page open. Another tab still shares the vision service and must follow its existing ownership rules.

These guards cover application links, including legacy brand and directory links. Browser Back, address-bar navigation, closing the tab and OS shutdown still use existing best-effort `pagehide` cleanup; the shared component cannot guarantee unload delivery or physical driver release. No physical release or participant trial is claimed.

## Integration boundary

`app-navigation.ts` owns the destination list, disclosure, status feedback and CSS. Entrypoints mount it after their viewer; game modules, session and vision are unchanged. Viewer mounts expose a read-only `navigationBlocker(): string | null`, which reports source or participant-window state. `NavigationStartup` retains the asynchronous Start barrier independently of local Stop state. Mole/Dodgeball/Runner acquisition checks this barrier directly as well as disabling controls, so synthetic or queued clicks cannot bypass it. A returned epoch is retained even with a fast `state:error` result; its failed scoped release remains retryable. The final ownership status takes precedence over ordinary round text, and cleanup refresh runs inside `finally` so a cancelled early return cannot leave stale controls.

Additional app-local owners can participate without importing the navigation module. Before a same-tab application departure, navigation dispatches a bubbling, cancelable `CustomEvent` named `motion-studio:navigation-check` on `#app` (or `body` when absent). Its detail is `{ reason: string | null }`. An owner listener on that root calls `preventDefault()` while starting, active, releasing, release-unconfirmed or ownership-unknown, and supplies actionable `event.detail.reason`. Otherwise it leaves the event untouched. Remove the listener on disposal. Keep pending state until late acknowledgement and release complete; do not clear ownership just because preview pixels stopped.

The merged maze floor-calibration repair ([issue #60](https://github.com/DupeisTaken/motion-capture-games/issues/60)) supplies its real capture blocker through the Maze owner's callable method, combined with the participant-window blocker. Its app-local click guard can also reopen setup to expose Stop/Retry. Integration tests and real-server synthetic checks exercise actual pending cancellation, failed late scoped release, acknowledged retry and unknown ownership. Physical calibration remains its own gate.

Runner retains both its independent `pendingStarts`/`startupUncertain` guards and the shared `NavigationStartup` barrier. The startup `finally` path finishes the navigation attempt and removes its pending generation. Current main's camera preview, body-width controls, spectator recovery, multiplayer and outcome effects remain in their owning components.

The acquisition follow-up adds eleven ownership regressions per overlay game: repeated Stop with pending/late acknowledgement, in-flight scoped cleanup, failed late release and retry, lost/invalid-JSON/missing-epoch/null responses (including a successful HTTP error-state body without an epoch), explicit ownerless rejection, fast worker error with an epoch, and disposal before acknowledgement. `node scripts/verify-game-acquisition.mjs --before` reproduces the two-request bug from PR head `3ff1487`; without `--before` it verifies the one-request barrier, retry recovery and unknown-ownership UI on English desktop/mobile. It uses synthetic HTTP/WebSocket boundaries and opens no camera.

A successful HTTP Start response must identify a nonblank owned epoch. An error-state body without that epoch still leaves ownership unknown; it cannot unlock acquisition or departure. An explicit rejected HTTP response without ownership remains retryable.

Runner keeps its independent startup and release guards while also consuming the shared pending/unknown barrier in Start and control locking. Four Runner regressions cover missing/empty/blank epochs in successful error-state responses and explicit rejected-HTTP recovery; its existing cancelled-start test also verifies direct acquisition blocking. The tracking console already validates its epoch before error-state handling and locks unknown/pending ownership; missing-epoch error-state and blank-epoch regressions confirm this without a console runtime change. `node scripts/verify-game-acquisition.mjs --runner --before` and `--runner` capture Runner desktop/mobile pending, failed-release/retry and malformed-success behavior.
