# Two-camera operator workspace

## Purpose and scope

[Issue #34](https://github.com/DupeisTaken/motion-capture-games/issues/34) adds `/rig.html` after [PR #31](https://github.com/DupeisTaken/motion-capture-games/pull/31). The user chose an operator workspace and synthetic rehearsal first, to understand and prepare more accurate rig-space XYZ for a possible virtual maze. A second angle supplies geometry only when calibration, exposure timing, identity and useful coverage are supported by evidence.

The workspace extends the existing Motion Studio design language. The [tracking console](diagnostic-viewer.md) keeps single-camera diagnostics; this route puts two camera roles, their observations, a rig map, estimated coordinates and evidence gates together. No maze game, scoring or simultaneous live capture is added. [The report](../reports/two-camera-workspace.html) records actual software/browser checks and before/after evidence.

## Rehearse paired observations

Rehearsal reads a bounded, versioned static dataset generated by `services/vision/tools/rig_rehearsal.py` using the existing [XYZ reconstruction implementation](player-xyz-experiment.md). The browser presents recorded samples; it does not duplicate triangulation or manufacture an accuracy improvement. Input observations, reconstructed estimates and independent synthetic reference truth remain separate.

Named primary/reference and secondary/supporting roles stay stable when a panel moves on a narrow screen. Camera-local track IDs and the associated synthetic rig identity are shown as different concepts. Joint names remain anatomical. Rig coordinates use right-handed meters: floor/display-center origin, X participant-screen-right, Y up, Z into the play area. Any image mirroring is a presentation choice and does not change those coordinates.

The two view diagrams show their own 2D observations. The floor map shows the root in XZ and its intended volume; Y remains explicit in the coordinate readout. The root is the midpoint of two accepted hips. A missing/rejected hip produces unavailable root XYZ, not zeros or last-known coordinates presented as current. Individual joint failures and pair-wide rejection have readable reasons. Movement playback and sample scrubbing are bounded presentation controls, not live source or inference FPS measurements; hidden pages pause rehearsal work.

Cases include normal observations, missing hips, uncertain identity, exposure timing problems, stale source input, weak geometry, changed calibration and hidden calibration bias. The bias case deliberately publishes an incorrect estimate despite plausible geometry; its reference comparison explains why physical scale checks matter. Simulated sample availability always remains separate from physically validated input.

## Plan the physical rig

Physical planning assigns distinct named-device references to primary and secondary roles. Explicit Refresh obtains device metadata without acquisition. Independent prefixed selectors preserve label relationships and device identity through list reordering; a disappeared selection clears rather than choosing a substitute. The same device cannot occupy both roles. Manual-index selection retains its documented reconnect limitations.

Planning mode starts no camera, invokes no capture endpoint and contains no live two-camera preview. It never inherits simulated coordinates, synthetic calibration or synthetic timing readiness. A single-camera inspection link returns to the existing console; operators start capture explicitly there. The current service owns one source, so two calls to its Start endpoint would replace that source rather than establish a pair.

Placement dimensions, intended volume and operator notes are planning information. Recording notes or checking role assignments is not evidence of exposure synchronization, metric scale, confirmed association or physical accuracy. The UI keeps these missing gates visible. Camera discovery failure, an absent service, duplicates and disconnection provide useful recovery without enabling XYZ.

## Evidence and future maze input

| Question | Required evidence |
| --- | --- |
| Can both views observe the intended movement volume? | Actual simultaneous views, supported joint coverage and physical boundary inspection |
| Is the scale and coordinate frame correct? | Camera/rig calibration bound to device identities and image geometry, plus independent held-out metric references |
| Were the observations exposed together? | Validated exposure timestamps or clock mapping with offset/drift, uncertainty, skew and age |
| Is this the same participant? | Cross-view association with explicit tentative/ambiguous/lost states; no ordering-based identity |
| Is a root usable now? | Current accepted hips, valid source/rig revision, quality gates and declared bounds |
| Can it control a maze? | Supported root-position error, useful update rate, physical play volume and externally measured feedback latency on the intended rig |

The workspace cannot turn these physical gates green through manual planning. Future integration needs one acquisition owner per device, bounded/latest-only pairing, scoped group lifecycle and partial-start cleanup, calibration loading/verification, exposure evidence and association. A future live diagnostic message belongs in the canonical versioned `contracts` boundary, rather than treating this static rehearsal format as a wire protocol. See [the physical XYZ protocol](player-xyz-experiment.md#physical-validation-protocol-open), [installation](installation.md) and [roadmap](roadmap.md).

## Development and verification

Run from the checkout root with the existing pinned environment. `pnpm dev` serves `/rig.html`; rehearsal works without starting cameras or downloading models. The generator supports `--check` so drift tests can compare the committed synthetic fixture with the actual Python solver. Existing `pnpm check` covers generated data/state/UI tests, types, lint and formatting; `pnpm build` includes the fourth HTML entry and verifies its emitted assets.

```text
pnpm rig:generate
pnpm rig:check
pnpm verify:rig
pnpm check
pnpm build
```

`rig:generate` recreates and formats the static fixture; `rig:check` checks semantic drift with an explicit numerical tolerance rather than requiring bit-identical linear algebra on every OS. `verify:rig` starts a task-owned Vite server and installed browser, uses synthetic device metadata for planning checks, and saves ignored screenshots/results under `reports/local/two-camera-workspace/`. `--report-only` validates the standalone report. No browser is downloaded automatically.

UI acceptance includes scenario/scrub/playback behavior, missing values and explanations, mode isolation, independent camera selectors, duplicate/disappearing devices, explicit discovery, keyboard controls and cleanup. Real Vite-server screenshots cover desktop, mobile and narrow English layouts. Browser tests use synthetic device metadata; they do not certify actual enumeration, calibration, camera modes or physical XYZ accuracy. Use [the delivery report](../reports/two-camera-workspace.html) for commands and outcomes actually run.
