Touch accepts hands/wrists or feet. Push accepts hips, hands or wrists with a valid toward-screen displacement. Each mole scores once. A held touch cannot collect a new mole without a fresh entry; every forward push attempt, including a miss, consumes its cycle until it returns to neutral. Consecutive hits earn a bounded streak bonus.

Hard mode samples 32 legal target positions and favors the largest minimum distance from the participant's available eligible contacts. All of the target remains inside the configured image-space area. Size and lifetime vary by difficulty. This boundary and the proposed 4cm neutral / 12cm push thresholds still need physical participant trials.

Architecture and failure behavior

games/mole-motion owns targets, collisions, active game time, score and seeded version-1 replay. packages/motion exposes named, observed contact points. packages/session binds one explicitly selected camera track to an anonymous player slot. The application alone composes these and controls the existing Python vision service. Games do not open cameras, import inference packages or know model landmark indices.

  • Both feet must remain visible. Otherwise the screen says Step back and also suggests correcting camera framing or clearing an occlusion; missing feet alone do not prove camera distance.
  • Missing, stale, uncertain or malformed input freezes round/target time and scoring. Recovery clears gesture history and uses an explicit 2-second countdown; starting uses 3 seconds. Hidden tabs pause too.
  • A spectator cannot automatically join. Lost/uncertain membership requires explicit rejoin. Changing track, source or calibration requires a fresh round, preventing a prior score moving to another participant.
  • One paired image/observation packet is requested at a time. Late camera-start acknowledgments and decoded bitmaps are released if their source was stopped. The client retains one image, not a frame backlog.
  • Source nanosecond differences and processing age are preserved. A bounded downward-only 20ms scheduling correction handles faster later delivery without rejuvenating delayed samples. Initial transit remains unknown; this is not exposure clock synchronization.
  • Video, normalized elliptical hit regions and anatomical contact labels share one contain-fit/mirror transform. Collisions use the current active browser game timeline; no physical latency compensation is claimed.

Remaining work and practical limits

The deliverable is a software prototype with camera contact support, not a certified installation. Live calibrated push input and per-participant reach setup require follow-up work; the existing XYZ experiment is relevant to depth calibration. Actual camera hit/framing quality, clothing/occlusion/height variation, physical push recognition, action-to-visible latency, three-player score attribution, platform hardware capacity and macOS operation were not measured. Synthetic scene rate and build timings are not camera-performance results.

Replay is an engine API with exact deterministic software outcomes for the same version, seed, commands and input. This page does not export participant recordings or provide a replay-import UI. The gameplay canvas uses a bounded 20Hz software update loop; no smoothness or end-to-end latency target is certified. The report itself needs no network connection; links to GitHub are optional references.
