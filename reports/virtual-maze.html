What changed and why

The existing workspace could inspect recorded two-view XYZ but had no maze game. The new /maze.html route generates reproducible layouts, renders the admin’s metric map and converts selected-facing wall clearance into one normalized visual/audio signal. Participants see intensity and input/round state without seeing the maze or route.

  • Easy/Medium/Hard control grid density; dimensions remain independently configurable from 5 to 10 m. Seeded perfect mazes are connected; loop-mode mazes retain a valid BFS solution while both declared canonical hand followers miss the interior goal.
  • Independent head and torso sliders rehearse the orientation toggle. Invalid selected direction, identity, position or timing pauses feedback and requires explicit recovery; no silent source substitution occurs.
  • Browser sound requires explicit activation, squares the normalized intensity and caps software gain at 0.12 × master volume. Pause/input loss/background presentation silence it immediately. Sound-pressure levels and speaker audibility were not measured.
  • Four named corners can be labelled on a local-only photo with pointer or keyboard percentages. A separately-tested rigid registration API accepts already-calibrated rig-floor coordinates. Photo pixels never become metric XYZ automatically.

The loop-mode check starts at cell 0 facing +Z. The left follower prefers left/straight/right/back; the right follower prefers right/straight/left/back. Each stops on a repeated (cell, heading), while BFS reaches the selected interior goal. The guarantee does not cover different starting headings, remembered routes or general search.

Runtime boundaries

The pure game owns generation, wall geometry and endpoint goal/contact queries. The motion layer owns pose validation and rig-to-maze registration helpers. The app owns UI, audio and lifecycle. No cameras or inference libraries are opened or imported by the game. The current UI uses an aligned synthetic frame and an explicit monotonic synthetic clock; physical-origin samples are unconditionally rejected. Live input integration must bind metric registration to a verified calibration and session identity.

Physical maze navigation remains gated. Simultaneous camera acquisition, exposure pairing, cross-view identity, measured XYZ and Head/Torso accuracy, cone-floor detection, supervised participant trials and a hardware buzzer interface remain future work. Endpoint rehearsal allows dragging across walls; it is not swept traversal or a physically verified route.

Before and after

Cones and the physical follow-up

Cone colors remain undecided. Human labels establish corner correspondence first. Future recognition can evaluate HSV thresholding, morphology/contours and calibrated cone floor-contact points under actual lighting. A floor homography applies to floor points, not elevated hips or heads. Photos and algorithm plausibility cannot certify scale, synchronized exposure or orientation.

The owning game design documents the primary OpenCV sources, metric corner convention, rejection screens and physical gates. M7-P1 through P4 in the roadmap retain issue-ready work for trusted capture/input, corner evidence, facing capability and supervised installation measurements.

Reproduce

Install with the pinned local environment and pnpm install --frozen-lockfile. Serve rehearsal using pnpm exec vite --host 127.0.0.1, then open http://127.0.0.1:5173/maze.html. Run pnpm verify:maze, pnpm check and pnpm build. Browser verification uses an already-installed Chrome/Edge; --chrome-executable selects another installation. Screenshots/results stay ignored under reports/local/virtual-maze/; this report embeds only synthetic examples.

Remaining limitations: no automatic cone detector, simultaneous live two-camera gameplay, physical head/torso estimator, hardware buzzer protocol, measured end-to-end latency, swept-path validation, native packaging or physical player trial. The separate participant page is a presentation boundary, not authentication for an untrusted operator.
